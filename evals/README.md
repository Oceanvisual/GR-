# Eval извлечения процессов (T036, R-17, R-21)

Гейт качества S3–S5 на живой LLM по эталонной разметке. В CI не входит: запускается вручную
до и после изменения промпта, модели, параметров разбиения или проверки цитат.

```bash
uv run python -m evals.run                    # все документы, сравнение с baseline.json
uv run python -m evals.run --only reg261      # один документ, без гейта
uv run python -m evals.run --cached           # кэш; при промахе возможен платный вызов LLM
uv run python -m evals.run --rescore evals/runs/<stamp>.json   # пересчёт после правки эталона
uv run python -m evals.run --update-baseline  # зафиксировать полный прогон как baseline
uv run python -m evals.run --strict           # плюс цели SC-003 / SC-002
uv run python -m evals.run --strict --budget-usd 3  # лимит одного живого прогона
```

### S6: инициативы (T066)

```bash
uv run python -m evals.run --s6                 # анализ с этапом S6 и его метрики
uv run python -m evals.run --judge              # то же и LLM-судья (модель [judge] в config.toml)
uv run python -m evals.run --judge --rescore evals/runs/<stamp>.json   # судья по сохранённому прогону
```

Детерминированные метрики (`metrics_opportunities.py`, критерии llm.md § S6):

| Метрика | Что меряет | Направление |
|---|---|---|
| `s6_reference_integrity` | доля предложенных инициатив без ссылок на несуществующие операции, проблемы и пункты | выше лучше; цель 1,0 |
| `s6_llm_for_classic_share` | доля LLM- и агентных решений там, где по каталогу хватает классической автоматизации | ниже лучше; цель ≤ 0,2 |
| `s6_simpler_alternative_share` | доля инициатив, рассмотревших решение проще своего | выше лучше |
| `s6_no_change_share`, `s6_initiatives` | доля процессов «оптимизация не требуется», число инициатив | только для сведения, без гейта |

Судья (`judge.py`, промпт `prompts/judge_initiative.md`) по каждой инициативе отвечает:
- обоснован ли выбор технологии (`s6_judge_grounded`);
- конкретна ли инициатива (`s6_judge_concrete`).

Вердикты кэшируются в `judge_cache.json` по хэшу модели, версии промпта и инициативы. Повторный
прогон и `--rescore` не платят. Файл коммитится вместе с baseline. Метрики S6 попадают в
baseline, если он снимался с `--s6`/`--judge`. Их регрессия даёт exit 1, как у метрик S3–S5. С
`--budget-usd` судья и S6 идут на модели `[live_budget]`.

Модель берётся из окружения, как у сервиса. Для дешёвого прогона её подставляют в команде:
`LLM_MODEL_EXTRACTION=anthropic/claude-haiku-5.5 uv run python -m evals.run`.
Результаты анализа лежат в `evals/.data`; открыть их в интерфейсе — `DATA_DIR=evals/.data uv run gr serve`.
Для проверки без вызовов LLM используйте `--rescore`. Фиксация baseline требует нового
полного прогона, проверенных экспертом эталонов и успешного гейта. Неполный анализ
считается ошибкой, даже если runner завершился со статусом `succeeded`.
Отчёт прогона — `evals/runs/<stamp>.json`: найденные и пропущенные процессы и операции,
лишние процессы, сроки не из текста.

`--budget-usd` выбирает модель и консервативные тарифы из `[live_budget]` в `config.toml`,
проверяет резерв стоимости перед каждым HTTP-запросом (включая fallback и repair), отключает
автоматические HTTP-повторы. Полученный счёт заменяет резерв; если счёт не получен,
резерв сохраняется. В отчёт записываются сумма счетов и консервативная верхняя граница.
Тарифы нужно проверить перед живым запуском. Лимит действует на один прогон; общий остаток
пользовательского бюджета фиксируется в `reports/test-budget.json`.

## Повторная детализация без вызовов LLM

`--rescore` пересчитывает только метрики. Для проверки текущего клиента, детализации и
валидатора на сохранённых ответах используйте отдельную команду:

```bash
uv run python -m evals.replay evals/runs/20261022T081359Z.json \
  --provider-host openrouter.ai --output evals/reports/replayed-processes.json
```

Нужны исходный отчёт и локальная БД с `llm_calls` (по умолчанию `evals/.data/gr.db`,
можно задать через `--database`). БД открывается только для чтения; сетевого клиента нет.
S3 берётся из сохранённого запуска, S4 и S5 выполняются заново. Параметр `--provider-host`
восстанавливает дополнительные поля запроса из конфигурации; запросы сопоставляются по
полному `request_hash`. Промах останавливает проверку. При изменении промпта или разбиения
нужен новый живой прогон. Невалидный ответ допускает только один записанный repair.

Команда создаёт отдельный JSON и файлы `*-review-1.md`, `*-review-2.md` для эксперта:
эталонные операции и сроки с исходным текстом, лишние процессы, отсутствие нужного пункта
в контексте S4. Статус экспертной проверки не меняется. Это воспроизводимая диагностика
сохранённых ответов, а не замена живого eval или основание для baseline.

## Метрики

По каждому документу; в гейте — среднее и минимум по документам.

| метрика | что считает |
|---|---|
| `process_recall` | доля обязательных процессов эталона, найденных моделью |
| `process_precision` | доля найденных процессов, совпавших с эталоном (обязательным или допустимым) |
| `operation_recall` | доля ключевых операций эталона в найденных процессах (SC-003) |
| `deadline_recall` | доля сроков эталона, найденных в процессах (информационно) |
| `verified_share` | цитаты-факты, прошедшие проверку, к ним плюс отклонённые утверждения (SC-002) |
| `deadlines_not_in_text` | сроки-факты, значения которых нет в процитированном тексте (SC-004, должно быть 0) |
| `coverage` | доля фрагментов, вошедших в процессы |
| `calls`, `in_tokens`, `out_tokens`, `latency_s` | расход |

Совпадение процессов: предсказанный процесс описывается фрагментами, которые цитируют его
название и действия операций. Он совпадает с процессом эталона, если не меньше половины этих
фрагментов лежит в корнях эталона (с поддеревьями) или если названия близки и есть общий
фрагмент. Пары подбираются один к одному: второй процесс на ту же процедуру — ложное
срабатывание, процесс «вся услуга целиком» не совпадает ни с чем.

## Эталон (`golden/*.json`)

- `roots` — метки фрагментов процесса, как их показывает интерфейс («п. 3.2», «ст. 8»); каждый
  корень берётся с поддеревом;
- `required: false` — допустимый процесс: его находка не штрафует точность, его пропуск не
  снижает полноту;
- `operations` — ключевые действия и фрагменты, где они названы;
- `deadlines` — сроки процесса из текста;
- `sha256` — редакция файла: эталон к другой редакции не применяется;
- `verified_by` — кто из экспертов проверил разметку (`null` — ещё не проверена; прогон об этом
  предупреждает).

`tests/unit/evals/test_golden.py` без LLM проверяет, что все метки есть в документе в том виде,
в каком его сейчас читает разбор, и что процессы эталона не делят фрагменты.

Как проверять эталон: для каждого обязательного процесса — то ли это деление на процедуры, что
даёт сам акт; нет ли процедуры, которой не хватает; ключевые ли операции; верны ли сроки и
единицы (`days` — тип дней в акте не указан). После правки — `--rescore` последнего прогона и
`--update-baseline`.

## Состав

| id | документ | тип, уровень |
|---|---|---|
| `reg261` | приказ Росимущества № 261, административный регламент | регламент, федеральный |
| `fz59` | ФЗ № 59-ФЗ «О порядке рассмотрения обращений граждан» | закон, федеральный |

Третий документ (R-21) — региональный или муниципальный административный регламент, будет
добавлен вместе с ним. DOC пока не разбирается (LibreOffice — T067), поэтому положение
Магинского сельсовета из dev-корпуса в набор не входит; закон Ленинградской области № 93-оз
описывает полномочия, а не процедуры. Отложенная выборка (`holdout/`) в eval не участвует.
